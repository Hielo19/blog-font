# 接入 Gin 后端

## 已具备的边界

- `services/blog/repository.ts`：异步内容读取接口 `getContent()`。
- `services/blog/local-repository.ts`：当前本地实现；不发起网络请求。
- `services/blog/index.ts`：页面的唯一内容入口，负责选择实现。
- `models/blog.ts`：前端需要的文章与首页展示结构。
- `services/api/`、`contracts/`、`services/blog/mappers/`：后续 HTTP、协议、字段转换的预留位置。

## 接入顺序

1. 与 Gin 后端确认公开文章、正文、媒体、站点信息等接口，将实际 OpenAPI 规范或已确认协议放在 `contracts/`。目前没有预设可调用的 URL、鉴权方式或响应字段。
2. 在 `services/api/` 增加 HTTP 客户端，统一基础地址、请求取消、非成功响应和错误处理。对响应做运行时校验，不能只用 TypeScript 类型断言认为远程数据有效。
3. 在 `services/blog/mappers/` 将后端传输数据转换成前端模型；保留当前正文段落、配图、来源和日期含义。当前正文按纯文本渲染；如果切换为 HTML 或 Markdown，应同时设计安全渲染流程。
4. 增加实现 `BlogRepository` 的远程数据实现，并在 `services/blog/index.ts` 切换。不得悄悄把网络失败当作成功并回退到旧文章；按所选加载方式处理错误。
5. 验证文章内容完整性、图片地址、时区、空内容、错误状态及原有滚动／返回位置行为。任意文章路由和分页仍需另行实现。

## 静态导出与更新方式

当前 `app/page.tsx` 在构建阶段读取数据。仅替换为 Gin 请求时，生成的网站仍是内容快照，后端文章更新后需要重新构建。构建期间 Gin 不可用应明确失败。

若要求发布文章后立即显示，可选择：

- 保留静态部署，在客户端增加数据加载层，处理加载、失败、空数据、取消请求及内容高度变化后的滚动同步。
- 调整为运行时服务端部署，再设计缓存和更新策略；需要同时更改当前静态导出配置。

这两种方式都不是本次结构整理已经启用的能力。

## 配置和边界

API 地址和环境变量应在正式接入时添加，并同步提供不含凭据的 `.env.example`。公开浏览器配置不能包含数据库密码、管理令牌或其他秘密。使用浏览器跨域请求时由 Gin 明确配置允许的来源；会话、登录和管理权限另行设计。

Gin 工程可独立建仓库；此仓库继续负责前端。如后续需要单仓库维护，再统一规划 `frontend/`、`backend/` 和开发脚本。本轮不生成空的 Go 服务、登录入口或不存在的公开接口。
